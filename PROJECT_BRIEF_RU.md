# TableSignal — задание на разработку

Начни реализацию локального Java-приложения для управляющего рестораном. Основная цель к показу 16 ноября — рабочее демо от посадки до заказа и понятный код, который можно открыть в IDE. Считай этот документ согласованным заданием. Принимай обратимые технические решения самостоятельно. Веди код и инструкции запуска на английском, отчёты владельцу — на русском. Если получишь исходники предыдущего этапа, проверь и продолжи их.

## Пользователь и основная операция

Хостес отмечает посадку. Менеджер на планшете смотрит зал, видит, какие столы ожидают подтверждения заказа от кассы, и открывает историю конкретной посадки. Гости могут смениться за одним и тем же столом несколько раз за смену. В демо используется вымышленный ресторан в Дурресе, два участка (зал и терраса), двенадцать столов. Время на экране Europe/Tirane. Для запуска достаточно обычного компьютера с браузером и сервером приложения. Все данные демонстрационные.

## Интерфейс

- Экран Floor во всю ширину. Сверху название заведения, дата и время смены, состояние связи с симулятором POS. Основная область — схема зала с номерами столов и понятной легендой. Отдельно показаны зал и терраса. На узком экране столы превращаются в список.
- У свободного стола серый статус Free. Для занятого — текст Seated и минуты с посадки. После 8 минут ожидания — янтарный статус Awaiting POS confirmation. При наличии заказа — Order confirmed и фактическое время ожидания. Для различения состояний использовать одновременно текст и цвет.
- Щелчок по столу открывает карточку визита сбоку, на телефоне — отдельной панелью. Показать номер стола, посадку, первый заказ, открытое предупреждение, историю событий и основание коррекции. Опоздавшее событие должно показывать обе отметки времени. Показывать разницу между временем до заказа и последующей задержкой передачи.
- Для свободного стола основное действие Seat guests. Для занятого доступны история и Close visit. После закрытия текущий стол свободен, историю можно открыть в списке завершённых визитов.
- Отдельный раздел Demo controls со сценарием по шагам и понятными действиями отключения и восстановления кассы, создания заказа и повтора отправки. Демонстрационные часы обновляются без реального восьмиминутного ожидания. Предусмотреть повтор демонстрации. Кнопки изменения демо-данных работают только в локальном demo-профиле.
- Верхняя сводка смены показывает занятые столы, открытые предупреждения и среднее время до первого заказа по визитам с известным заказом. Пустое значение показывать прочерком. Стиль спокойного рабочего интерфейса: светлый фон, тёмный текст, заметные времена и номера, клавиатурный фокус, объяснимые сообщения об ошибках.

## Стек и организация

Java 21, Maven, Spring Boot, Spring Web, PostgreSQL, Flyway, JUnit 5. Один серверный процесс. Для первого интерфейса — HTML/CSS и обычный JavaScript, поставляемые вместе с приложением. Небольшой REST API и обновление зала опросом раз в несколько секунд. Хранить моменты в UTC (Instant в Java, timestamptz в PostgreSQL), локализовать в UI. Инъекция Clock для расчётов и тестов. Docker Compose для старта приложения и PostgreSQL; том для данных, localhost для демо. Разделить предметную логику, приём событий, хранение, HTTP и веб-ресурсы. В Git хранить исходники, миграции и маленькие фикстуры. Репозиторий должен открываться как Maven-проект в IntelliJ IDEA.

## Данные, правила и API

Стол и визит — отдельные сущности. Основные поля визита: visitId, venueId, tableId, seatedAt, closedAt. Каждое сообщение от источника содержит source, eventId, visitId, тип и occurredAt. Сервер самостоятельно ставит receivedAt. События — посадка, заказ, закрытие. История предупреждения хранит момент открытия и причину закрытия. Один стол допускает один активный визит; контроль должен работать при одновременных посадках.

Идентичная повторная доставка события с тем же ключом (venueId, source, eventId) успешна и не создаёт вторую запись или второй побочный эффект. Тот же ключ с другим содержанием даёт явный конфликт. Сохранение принятого события и изменение состояния объединить в транзакцию; обеспечить уникальность в БД. Для визита фактическое ожидание — разница между посадкой и самым ранним допустимым временем заказа. Поздняя доставка заказа уже завершённого визита корректирует историю именно его. Описать поведение для заказа раньше посадки, после закрытия по времени события, конфликтующих ключей и неизвестных визитов. Отрицательные интервалы не должны попадать в показатели.

Предупреждение открывается один раз на визит при достижении порога 8 минут, если заказ всё ещё неизвестен и визит активен. При поступлении заказа сохранить исходное предупреждение. Если касса зафиксировала заказ до порога, объяснить запоздалую доставку. Если заказ сделан после порога, отметить фактическое превышение. Новые события и фоновые проверки безопасны при повторе. Для статистики использовать время события; отдельно показывать задержку доставки. По событию кассы нельзя доказать, когда официант подошёл к гостям.

Предусмотреть приём событий, чтение карты зала, истории визита и статистики смены. Зафиксировать фактические маршруты и простые примеры запросов в README. Для ошибок использовать понятные статусы HTTP и короткую причину. Историческое время независимо от часов ноутбука.

## Контрольный сценарий

| Шаг | Событие | Видимый результат |
|---|---|---|
| 19:00 | Посадка за №12 | Новый визит, ожидание запущено |
| 19:04 | Отключённая касса локально принимает первый заказ | Интерфейс ещё ожидает подтверждение |
| 19:08 | Достигнут порог | Одно предупреждение |
| 19:10 | Восстановилась связь, доставлен заказ с occurredAt 19:04 | Ожидание 4 минуты, задержка доставки 6 минут, предупреждение закрыто с объяснением |
| 19:11 | Приходит идентичный повтор | Один заказ и одно закрытие, показатели прежние |

Дополнительная проверка: закрыть старый визит, посадить следующих гостей за тот же стол, дослать заказ старого визита. Новый визит продолжает ждать собственный заказ.

## Приёмка, доставка и порядок работ

1. Сначала предметная модель и тесты с управляемыми часами. Проверить заказ до порога, ровно 8 минут без заказа, заказ с задержкой, повтор и конфликт идентификатора, пересадку за тот же стол и более ранний заказ, полученный позже другого.
2. Затем миграции, HTTP и интеграционные проверки PostgreSQL. Важные проверки — параллельный повтор одного сообщения и запрет двух активных визитов за столом. После перезапуска история остаётся доступной.
3. Подключить экран, демо-кассу и часы к тем же обработчикам, которыми пользуется API. Проверить сценарий в интерфейсе. Проверить маленький экран и восстановление после ошибки.
4. Подготовить запуск командой docker compose up --build, англоязычный README с архитектурой, примерами, тестами, ограничениями и пятиминутным маршрутом показа в IDE. Проверить запуск в чистом каталоге, сообщить отдельно результаты реально выполненных проверок и оставшиеся ограничения.
5. Когда базовый сценарий готов, расширять продукт в следующем порядке: история и сравнение смен, кухонные этапы, несколько заведений и роли, уведомления. Интеграция с реальной POS и получение событий занятости/уборки от камер — отдельные последующие этапы. Для первого релиза используются только синтетические события. Публичный деплой и платные сервисы требуют отдельного решения владельца.
